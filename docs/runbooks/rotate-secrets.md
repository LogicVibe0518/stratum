# Runbook: rotate every secret

Use it when a host that stores Stratum's secrets is breached (Railway, 21 Oct 2026), when a key
leaks (a screenshot, a commit, a chat), when someone with access leaves, and once a quarter as a
drill. Assume every value the host held is known to the attacker; rotate at the source, not just
on the host.

Order: **contain** (kill the leaked values) → **restore** (new values everywhere) → **verify**
(new values work, old ones are refused) → **investigate** (was anything used?) → **harden**.
A short planned outage is better than a leaked key that still works: Stratum has no live users
who need it up in the middle of a rotation.

## The inventory

| Variable | Lives in | Someone holding it can | Rotate at |
|---|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` (a secret key, `sb_secret_...`) | worker host, `.env.worker` | read and write **every** row and file of every agency (bypasses RLS) | Supabase > Settings > API Keys |
| `SUPABASE_JWT_PRIVATE_KEY` (ES256 JWK) | worker host, `.env.worker` | sign in as **any** user until revoked | Supabase > Settings > JWT Keys |
| legacy JWT secret (`SUPABASE_JWT_SECRET`, retired 26 Oct 2026) | nowhere now | sign in as anyone, and it signed the legacy anon and service-role keys | JWT Keys: revoked |
| `SUPABASE_ANON_KEY` (publishable, `sb_publishable_...`) | API and worker hosts, `.env`, the browser | nothing by itself: it is public by design; RLS decides | API Keys (rotate if abused) |
| `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, `FAL_KEY`, `ELEVENLABS_API_KEY` | API and worker hosts, `.env` | spend our money on their models | each provider's key page |
| `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` | API and worker hosts, `.env` | read our AI traces (prompts include clients' briefs) and write fake ones | Langfuse > project > API keys |
| `SENTRY_DSN` | hosts | send fake errors (low) | Sentry > project > Client keys |
| Railway account, GitHub, Supabase and provider logins | people | everything above | each site's security settings; 2FA on all |

Not secrets: `SUPABASE_URL`, `LANGFUSE_BASE_URL`, `ENV`. `DATABASE_URL` in `.env` is the local
test database only; the production database password is not stored on any host.

The worker holds the two strongest credentials. Keep them out of the API's environment (the API
drops a service-role key it finds, at import), and use separate provider keys for local and hosted
use, each with a spend limit, so one leak kills one key.

## 1. Contain

1. **AI providers.** On each provider, revoke every key the host held, then check the usage page
   for the exposure window. Create new keys with a spend limit, one for the host and one for local
   use.
2. **Langfuse.** Delete the project's API key pair; create a new one.
3. **Supabase.** Settings > API Keys: create a publishable key and a secret key (name it
   `worker`). Note the legacy keys' "last used" times for the record, then **deactivate** the
   legacy anon and service-role keys (reversible). Settings > JWT Keys: move the legacy JWT
   secret to **revoked** (reversible; deleting is not allowed, and never needed). Key state
   changes are throttled for about 5 minutes between actions.
   After this, everything leaked from the host is refused, and Stratum is down until step 2.

## 2. Restore

1. Make the worker's signing key on your own machine, never in a chat or on a shared screen:
   `uv run python -m stratum_worker.queue.identity --new-key`.
2. Supabase > Settings > JWT Keys: create a standby key by importing that JSON, then rotate it in.
   Then create another standby key (generated by Supabase) and rotate again: Supabase's own key
   signs everyone's sessions, and the worker's key stays trusted only for the worker's tokens.
   Revoking the worker's key later then signs out nobody.
3. Put the new values in `.env`, `.env.worker` and the hosts (sealed variables where the host has
   them):

   | Variable | API | worker |
   |---|---|---|
   | `SUPABASE_ANON_KEY` = the publishable key | yes | yes |
   | `SUPABASE_SERVICE_ROLE_KEY` = the secret key | **no** | yes |
   | `SUPABASE_JWT_PRIVATE_KEY` = the JSON from step 1 | **no** | yes |
   | AI provider keys, Langfuse keys | yes | yes |

   Remove `SUPABASE_JWT_SECRET` everywhere. Clear the terminal that printed the key.
4. Redeploy both services.

## 3. Verify

- `uv run python -m stratum_worker.queue.identity --check <your user id>` prints "ok: the worker
  would act as ...". A 401 means the project does not trust the signing key yet (step 2.2).
- `curl -s https://<api host>/healthz` reports Supabase and every AI task configured.
- Sign in on the site, open a post, make one change, make one draft (the worker settles the job).
- In Supabase, the legacy keys show as deactivated and the legacy secret as revoked; their "last
  used" times stop moving.

## 4. Investigate

Supabase keeps a day of API logs on this plan, so check as soon as the breach is known.

```sql
-- Writes since the window opened (run in the SQL editor; read-only)
select 'auth.users created', count(*) from auth.users where created_at >= '<window start>'
union all select 'sign-ins', count(*) from auth.users where last_sign_in_at >= '<window start>'
union all select 'posts changed', count(*) from stratum.posts where updated_at >= '<window start>'
union all select 'jobs', count(*) from stratum.jobs where created_at >= '<window start>'
union all select 'files added', count(*) from storage.objects where created_at >= '<window start>';
```

In Logs > Explorer (edge logs): group requests by path, role, user agent and the caller's network
(`request.cf.asOrganization`). Every service-role request should be `POST rpc/claim_job` or a
`PATCH jobs` (settling a job) from the worker's host; anything else is not us. Also check each provider's
usage page, the host's audit log, and GitHub (Settings > Security log, installed apps, the repo's
deploy keys, webhooks and collaborators).

Reads leave no trace in the tables: if the secret key leaked, treat every client's data as read,
and tell anyone whose data it is.

## 5. Harden (after the incident)

- Spend limits on every provider key; separate keys for local and hosted use.
- Logs that outlive the breach: keep at least a week (a log drain or a paid plan).
- The worker polls `claim_job` several times a second while idle; backing off when the queue is
  empty makes the logs readable and the bill smaller.
- Rehearse this runbook once a quarter and time it.
